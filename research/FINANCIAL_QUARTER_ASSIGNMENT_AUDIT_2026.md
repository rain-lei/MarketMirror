# 2020 问答大表的“季度”分组时序审计

**结论：来源列 `季度` 与回复日期的分桶完全一致，不能用作财务报告期或事前财务特征。** 对用户提供的 2020 问答大表全部 390,608 条来源行，按下面这条从数据中归纳的规则重建 `季度`，错配为 **0**：

| 回复日期 | 来源 `季度` | 行数 |
|---|---:|---:|
| 2020-01-01 至 2020-03-30 | 1 | 101,348 |
| 2020-03-31 至 2020-06-29 | 2 | 108,432 |
| 2020-06-30 至 2020-09-29 | 3 | 99,243 |
| 2020-09-30 及以后 | 4 | 81,585 |

季末边界比通常的自然季度结束日早一天：2020-03-30 的 1,836 条回复列为 1，03-31 的 2,177 条列为 2；06-29/06-30 分别为 2/3，09-29/09-30 分别为 3/4。此表还包括 **9,489 条在 2021–2023 年才回复**的问答，全部列为 4。回复日期最晚为 2023-08-30，但 `季度` 没有年份。上述是对这份文件的**事后经验规则**，不是数据提供方发布的字段定义；其日期边界可能来自原始切分脚本，无法仅凭本表确定生成原因。

作为对照，`季度` 与提问所在自然季度相同的有 353,875/390,608 条，另有 **36,733 条不同**；与 2020 年回复所在自然季度相同的有 376,021/381,119 条，剩余 5,098 条错配全部出现在 03-31、06-30、09-30 三个边界日。数据支持“按回复日期分组”的解释，却**不证明**同一行的 66 个财务值来自相应财报季度。财务字段还缺报告年份、原始单位、数值变换、期间类型、单项指标发布时间与修订历史。现有 12,287 份去重快照仍全部为 `unverified`，报告期和公开时间仍为空。

[审计程序](data_pipeline/audit_financial_quarter_assignment.py)先核对原始工作簿、已提取 SQLite、财务提取报告及字段清单的 SHA-256，并检查 SQLite 完整性、快照未验证状态与来源引用数，再只读取 `季度`、提问日期和回复日期做聚合。没有读取或归档问答正文。结果保存在 Git 忽略的 `research_outputs/financial_2020/quarter_assignment_audit_v1.json`；`python -m research.data_pipeline.audit_financial_quarter_assignment --audit-existing` 可重算，原始工作簿移位时可传 `--source`。工作簿身份及首例年报对账见[附件结构核验](USER_WORKBOOK_SOURCE_AUDIT_2026.md)。

因此，`financial_snapshot.source_quarter_hint` 继续仅作**来源分组和去重提示**。在找到提供方的字段定义、逐项财报来源和可见时间之前，不把这些快照转换为 `financial_quarter`、财务比率、预测特征或 Agent 决策变量，也不把问题发生时间当作财务披露时间。该规则不能修复先前已发现的时点泄漏风险，只是更精确地说明风险来自哪里。
